# Transformations

_Describe what your gateway changes at each checkpoint, in the same terms as the rest of your tracking plan._

<Callout type="info" emoji="🚧">
  Gateways are in closed beta. Reach out at [support@avo.app](mailto:support@avo.app) or in the chat bubble in the app to request access and share feedback.
</Callout>

A transformation records what a [gateway](/data-design/avo-tracking-plan/gateways) does to events at one checkpoint. Avo applies the transformations in the order an event travels, so it can work out what each checkpoint should receive.

## Define and update transformations

You write transformations through the [Avo MCP](/reference/avo-mcp/overview) on a branch, yourself or with your agent, and review and merge them like any other change. The branch diff shows each changed rule as before and after. Describe them the way you'd explain your tags to a colleague. For example:

> At the Pinterest output, send `transaction_id` as `order_id`. Stop sending `search_query` to every ad platform output. Require `tier` on product views sent to Meta.

> At the gateway, add `event_id` to every event.

> Our Meta tag now sends `content_ids` instead of `contents`. Update the Meta output on a new branch.

> Here's an export of our GTM container. Compare what each tag sends with our tracking plan and add the differences as transformations on a new branch.

See [Set up a gateway](/data-design/avo-tracking-plan/gateways/set-up-a-gateway) for the full setup.

## Where a transformation can sit

| Checkpoint | Use it for | Example |
| --- | --- | --- |
| An input | What the gateway does to events from one source as they arrive | The Segment SDK adds properties such as the IP address to every event, and each SDK adds different ones, so they belong on that source's input |
| The gateway | What happens to every event before it fans out to the outputs | The gateway adds an `event_id` to every event before sending it anywhere |
| An output | What one destination receives | Meta receives `Order Completed` as `Purchase`, and Pinterest receives `transaction_id` as `order_id` |

An event's shape at an output is the result of every transformation on its path: its source, then the input it entered through, then the gateway, then that output. A checkpoint with no transformation passes events through unchanged.

An input transformation doesn't change what the source sends. The event on the source still says what developers should send. If a source should stop sending a property, change the event on that source instead of adding a rule at the input.

## What a transformation can change

### Events

- **Rename.** Send an event under a different name from a checkpoint on, for example `Order Completed` sent to Meta as `Purchase`. Renames are set per event.
- **Allow.** At a checkpoint that only lets listed events through, list the events that pass. See [Choose what passes through](/data-design/avo-tracking-plan/gateways/set-up-a-gateway#2-choose-what-passes-through).

### Properties

Each property rule applies to every event that passes through the checkpoint and carries the property. The Transformations tab shows what each rule does next to it.

- **Add** (`enrich` in the MCP). The gateway adds the property to events that don't already send it. Use it for values the gateway fills in, such as a click id read from a cookie. Shown as "Added at this stage".
- **Require** (`require`). Every event entering the checkpoint must send the property. It never adds it, so the sources that feed the checkpoint have to. For example, if a Meta audience is built on `tier`, a Require rule on `tier` at the Meta output says that every product view reaching Meta must carry it. If a source doesn't send `tier`, that's the gap to fix at the source. Shown as "Required of every entering event".
- **Tighten** (`tighten`). Constrains the property only on events that already send it, for example by pinning a value or disallowing values. It never adds the property. At an allowlist checkpoint, a Tighten rule with no constraints keeps the property on the events that already send it. Shown as "Tightened where already sent".
- **Rename.** Send the property under a different name, for example `transaction_id` sent as `order_id`.
- **Set presence.** Say whether the property is always sent or sometimes sent from this checkpoint on. Always sent needs a Require rule.
- **Pin a value.** Send the property with one fixed value.
- **Disallow values.** Rule out values that the property otherwise allows.
- **Match a regex.** Require the value to match a regular expression.
- **Stop sending.** The property isn't sent from this checkpoint on. This is different from clearing the property's rule: clearing removes this checkpoint's change, so the property goes back to whatever it inherits from earlier on the path.

### Property bundles

- **Attach.** Attach a [property bundle](/data-design/avo-tracking-plan/properties#event-property-bundles) at a checkpoint to send its properties from there on.
- **Stop sending.** Stop sending a bundle's properties from a checkpoint on. As with properties, this is different from clearing the bundle's rule, which goes back to what the checkpoint inherits.

## Limits during the closed beta

- Inspector checks which events and properties reach a checkpoint, whether each property is present and its type. Pinned values, disallowed values and regex rules are part of the checkpoint's description, but Inspector doesn't check them at gateway checkpoints yet.
- A property rule applies to every event at its checkpoint that carries the property. You can't yet make an exception for one event.
